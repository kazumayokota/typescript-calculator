# React・TypeScript 計算機 実装手順書

## 1. 目的

詳細設計書を原本として、計算機をReactとTypeScriptで新規実装する。本書はAI駆動開発で設計逸脱、暗黙変換、計算誤差、確認漏れを防ぐためのフェーズ別手順を定義する。

設計書そのものは変更しない。Reactアプリケーション、ソースコード、テスト、設定ファイルを別の成果物として作成する。

## 2. 基本方針

- 詳細設計書と、利用者が明示的に承認した追加仕様を正とする。
- Reactコンポーネントを旧設計のUserForm相当とする。
- Reactに依存しないTypeScriptモジュールを旧設計の標準モジュール相当とする。
- 入力・表示は文字列で保持し、計算時だけ検証済み文字列をDecimalへ明示変換する。
- 計算結果は小数点以下最大15桁とし、16桁目以降を四捨五入する。
- JavaScriptの`number`による直接計算は避け、既定では`decimal.js`を使用する。
- 数式文字列を`eval`などで実行しない。四則演算を明示的に分岐する。
- 型・状態遷移の設計後は、React画面、共通計算処理、イベント結合の順で実装する。
- 各フェーズの完了条件を満たしてから次へ進む。

## 3. 設計書から確定している仕様

### 3.1 画面項目

- 計算1表示
- 計算2表示
- 数字ボタン：`0`～`9`
- 小数点ボタン：`.`
- 演算子ボタン：`+`、`-`、`×`、`÷`
- 全体クリアボタン：`C`
- 部分クリアボタン：`CE`
- 計算ボタン：`=`

### 3.2 計算方式

- 演算子の優先順位を使わず、左から順に即時計算する。
- `2 + 3 × 4 =`は`20`となる。
- 演算子の連続入力では、直前の演算子を新しい演算子に置き換える。
- `=`は左右の値がそろっている場合だけ計算する。
- `C`は両方の表示を消去し、`CE`は計算2表示だけを消去する。
- 0除算の結果は設計書どおり`0`とする。

### 3.3 追加仕様

- 結果の小数部は最大15桁とする。
- 16桁目以降は四捨五入（round-half-up）する。
- 結果末尾の不要な`0`は表示しない。
- `-0`は`0`として表示する。

## 6. フェーズ2：型と状態遷移の設計

### 実施内容

1. 演算子を文字列一般ではなくunion型で定義する。
2. 画面状態を`CalculatorState`として定義する。
3. 操作をdiscriminated unionの`CalculatorAction`として定義する。
4. `useReducer`で扱う状態遷移表を作る。
5. 表示文字列と計算値を別の役割として設計する。
6. 状態分類S0～S3の全actionについて遷移先を定義する。
7. 設計結果を`型・状態遷移設計書.md`へ記録し、レビューしてから実装へ進む。

### 型の例

```ts
export type Operator = "add" | "subtract" | "multiply" | "divide";

export type CalculatorState = {
  strDisplay1: string;
  strDisplay2: string;
};

export type CalculatorAction =
  | Readonly<{ strType: "digitInput"; strDigit: Digit }>
  | Readonly<{ strType: "decimalPointInput" }>
  | Readonly<{ strType: "operatorInput"; strOperator: Operator }>
  | Readonly<{ strType: "calculate" }>
  | Readonly<{ strType: "clearAll" }>
  | Readonly<{ strType: "clearEntry" }>;
```

実装時には、全関数の引数型と戻り値型を明記する。計算途中の値を無条件にJavaScriptの`number`へ変換しない。

### 状態遷移で確認する操作

- 空の状態で数字を押す。
- 空の状態で小数点を押す。
- 空の状態で演算子を押す。
- 数字入力後に演算子を押す。
- 演算子を続けて押す。
- 左右の値がある状態で別の演算子を押す。
- 左右の値がある状態で`=`を押す。
- `C`と`CE`を押す。

### 完了条件

- 設計書の各分岐と状態遷移が対応している。
- 不明な状態を「一般的な電卓ならこうなる」という理由で補っていない。
- 状態、action、不変条件、丸め手順、UI propsが設計文書に記録されている。
- このフェーズでは機能コードを実装していない。

## 7. フェーズ3：React画面の実装

詳細設計書の画面イメージを先にReactコンポーネントとして再現する。このフェーズでは共通計算処理、reducer、状態更新イベントを実装しない。

### 実施内容

1. `CalculatorDisplay`で計算1と計算2の2段表示を作る。
2. `CalculatorButton`をネイティブ`button`要素で作る。
3. `CalculatorKeypad`で設計書どおりに全ボタンを配置する。
4. `Calculator`で表示とキーパッドを構成する。
5. CSS Gridで元の画面配置を再現する。
6. `=`を設計書の画面イメージどおり縦長にする。
7. `0`と小数点の位置を設計書に合わせる。
8. 型・状態遷移設計書で定義したUI propsを使用する。
9. UI確認用の表示値はfixtureとして明示し、業務状態として保持しない。

### UI上の安全対策

- すべての操作要素に`button`要素を使用する。
- 各ボタンに用途が分かるアクセシブルな名前を付ける。
- 表示領域には計算結果が更新されることを支援技術へ伝えられる属性を設定する。
- キーボードフォーカスを視認可能にする。
- 文字列をHTMLとして挿入しない。
- 長い値が画面外へ破壊的にはみ出さないようにする。

### このフェーズで実装しないもの

- 数字や小数点の文字列連結。
- Decimal変換と四則演算。
- 演算子置換。
- reducerとstate更新。
- ボタン押下による業務動作。
- 一時的な計算ロジックや、後で捨てるイベント処理。

### 完了条件

- 設計書にないボタンが追加されていない。
- 2段表示と全ボタンの配置が設計書と一致している。
- マウス、タッチ、Tab、Enter、Spaceでbutton要素を操作できる。
- 空表示と長い表示値でレイアウトが破綻しない。
- 計算処理、reducer、状態更新イベントがUIに混在していない。
- UIの構造とアクセシビリティに関するコンポーネントテストが成功する。

## 8. フェーズ4：共通計算処理の実装

UIフェーズ完了後に実施する。処理は`src/logic`へ配置し、ReactやDOMを参照させない。

### 実装順序

1. `Digit`、`Operator`、`OperatorSymbol`、`CalculatorState`、`CalculatorAction`を設計書どおりにコード化する。
2. 入力可能文字を検証する処理。
3. 数字を表示文字列へ追加する処理。
4. 小数点の重複を防止する処理。
5. 先頭の不要な`0`を抑制する処理。
6. 演算子を設定・置換する処理。
7. Decimalへ明示変換する処理。
8. 四則演算を演算子ごとに明示実行する処理。
9. 小数点以下15桁で四捨五入する処理。
10. 末尾の`0`と末尾の小数点を除去する処理。
11. `-0`を`0`へ正規化する処理。
12. reducerで`C`、`CE`を含む全actionを処理する。

### 丸め処理

- Decimalのround-half-upを明示指定する。
- 小数点以下15桁へ丸める。
- 有効数字15桁への丸めと混同しない。
- 入力途中の値は丸めず、計算結果を表示するときに丸める。

### 禁止事項

- `eval`または`Function`による数式評価。
- `number`同士の直接計算による小数演算。
- 未検証文字列への`parseFloat`。
- `==`による暗黙変換を伴う比較。
- エラーを握りつぶして`0`を返す処理。0除算の`0`は明示された仕様分岐として実装する。
- 共通ロジックからReactコンポーネントまたはDOMを参照すること。

### 完了条件

- 型・状態遷移設計書に定義したS0～S3と全actionが実装されている。
- 計算処理とreducerの単体テストがすべて成功する。
- 計算モジュールにReactのimportがない。
- すべての変換がコード上で明示されている。
- UIコンポーネントはこのフェーズの実装によって変更されていない。

## 9. フェーズ5：イベントと状態管理の結合

UIと共通計算処理の両方が完了した後に実施する。

### 実施内容

1. 各数字ボタンから数字入力actionをdispatchする。
2. 小数点ボタンから小数点actionをdispatchする。
3. 各演算子を内部の`Operator`へ明示的に対応付ける。
4. `C`、`CE`、`=`をそれぞれ別actionにする。
5. 表示用記号`×`、`÷`と内部の演算種別を分離する。
6. reducer以外から状態を直接書き換えない。

### 完了条件

- すべてのボタン操作が設計上の共通処理へ対応している。
- 同じ計算処理を複数コンポーネントへ重複実装していない。

## 10. フェーズ6：テスト

### 10.1 単体テスト

最低限、次を確認する。

| 操作・計算 | 期待結果 |
| --- | --- |
| `1 + 2 =` | `3` |
| `5 - 8 =` | `-3` |
| `3 × 4 =` | `12` |
| `8 ÷ 2 =` | `4` |
| `2 + 3 × 4 =` | `20` |
| `1 + + 2 =` | `3` |
| `5 + =` | 計算しない |
| `. 5` | `5` |
| `1 . . 5` | `1.5` |
| `0 0 1` | `1` |
| `8 ÷ 0 =` | `0` |
| `0.1 + 0.2 =` | `0.3` |
| `1 ÷ 3 =` | `0.333333333333333` |
| `2 ÷ 3 =` | `0.666666666666667` |
| 負のゼロになる計算 | `0` |

### 10.2 コンポーネントテスト

- ボタン押下で表示が更新される。
- `C`で両表示が消える。
- `CE`で計算2表示だけが消える。
- 演算子の連続押下で末尾演算子が置き換わる。
- `=`の連続押下で前回演算を繰り返さない。
- ボタンにアクセシブルな名前がある。

### 10.3 境界値テスト

- 小数部14桁、15桁、16桁。
- 16桁目が`4`、`5`、`6`の場合。
- 非常に大きい整数部を持つ値。
- 結果末尾に複数の`0`がある場合。
- `-0`となる可能性がある場合。

### 完了条件

- 全要件IDに対応するテストがある。
- 失敗テストを削除、skip、期待値変更で回避していない。

## 13. AI作業時の停止条件

次の場合、AIは推測で実装を続けず、影響範囲を整理して利用者へ確認する。

- 設計書と追加仕様が矛盾する。
- 画面上の観測可能な動作を変更する必要がある。
- 新しい依存ライブラリや外部サービスが必要になる。
- テスト期待値を設計から一意に決められない。
- 調査時間が事前に決めた上限を超える。
- セキュリティ設定、型チェック、lint、テストを弱めないと進められない。
